# Аудит интеграции HNSW — 29 октября 2026

## До изменения

Семантический поиск уже был подключён к backend. Создание вычисляло
document-вектор названия через `/api/embed`, поиск — query-вектор.
`FindSemantic` использовал pgvector cosine `<=>`, точную сортировку,
абсолютный порог `0.16`, отступ от лучшего `0.03` и до 20 результатов.
Буквальные результаты дополнялись семантическими без дубликатов.

В схеме были PK `tasks(id)`, PK `task_embeddings(task_id)` и B-tree
`tasks(user_id,date,time)`. HNSW/IVFFlat и триграммного индекса названий
не было. Веса E5 и нормализация уже были реализованы.

Пробелы: отсутствовал векторный индекс, не было CLI для дозаполнения
векторов. Создание сохраняло вектор без повторной проверки названия.
README обещал ошибку при недоступности embeddings, тогда как сервис
сохранял буквальный поиск.

## Решение

Добавлен конкурентно создаваемый HNSW с cosine. Exact остаётся явно
точным и используется как эталон, режим по умолчанию и резервный путь.
В HNSW выбираются дополнительные кандидаты, после чего сохраняются
существующие пороги и лимит. Все ограничения владельца, пространства
эмбеддингов и периода остаются внутри SQL получения кандидатов.

Для выбора exact на малых наборах проверяется верхняя граница количества
подходящих задач, без чтения векторов. Порог установлен в 1500 после
сравнения крупного, среднего, редкого владельцев и узкого периода.
Это начальная настройка; распределение реальных данных может требовать
другого порога. Настройки ANN локальны для транзакции и не меняют
переиспользуемые соединения пула после её завершения.

Backfill использует UUID keyset pagination, ограничивает число задач
и одновременных запросов encoder, поддерживает dry-run. Запись вектора
проверяет актуальность названия под блокировкой строки. Такой же метод
используется после создания задачи. Переименование и удаление сохраняют
существующие транзакционные гарантии.

## Проверка

Проверки проводились на отдельных PostgreSQL 16 / pgvector 0.8.7 и Redis,
с локальным E5. Рабочая БД и платная LLM не использовались.
Миграция прошла Up/Down/Up; индекс также построен на 10000 векторов.
Тесты проверяют фильтры, несовместимую версию, отсутствие совпадений,
ANN timeout/fallback, отсутствие утечки настроек, конкурентную запись,
устаревшее название и каскадное удаление embeddings.

Воспроизводимый benchmark содержит 10000 нормализованных синтетических
384-мерных векторов, 4 владельцев и 40 запросов на сценарий. Это оценка
поиска соседей и SQL, а не оценка качества языковой модели.
План PostgreSQL подтверждает HNSW для крупного владельца и обычные
планы для части селективных запросов. Exact не использует ANN.

## Практические ограничения

ANN может пропустить часть точных соседей даже при непустой выдаче.
Общий индекс требует проверки на реальной селективности владельца
и версии модели. Автоматическая проверка полноты каждого ответа
посредством exact уничтожила бы смысл ускорения; вместо неё предусмотрены
сравнительные измерения и переключаемый режим.

Индекс ускоряет retrieval, но не улучшает понимание текста моделью E5.
Кодируется по-прежнему только название задачи. Изменение модели,
нормализации, переход на L2, reranker, отдельная векторная БД и
ускорение `ILIKE` в эту интеграцию не входят.

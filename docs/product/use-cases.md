# Use Cases

Реальное поведение продукта по контрактам и коду. Требования — по идентификаторам [PRD](prd.md). Все сценарии предполагают действующую сессию.

## Use Case 1. Создание задачи, напоминания или встречи (Core MVP)

Актор: пользователь, часто с занятыми руками.

Цель: зафиксировать запись свободной формулировкой, без ручного ввода полей.

Предусловие: пользователь авторизован.

Основной поток:

1. Пользователь отправляет текст в POST /api/task (или WAV — сначала распознавание речи).
2. Ассистент определяет тип записи, название, дату и время.
3. Данных достаточно: backend сохраняет запись и возвращает 201 с подтверждением.

Альтернативный поток 1: данных не хватает (нет времени у встречи) — ассистент задаёт вопрос, черновик сохраняется. Ответ пользователя с тем же task_id продолжает диалог, уже названные поля не теряются.

Альтернативный поток 2: время расплывчатое («после обеда») — требуется ещё одно уточнение.

Альтернативный поток 3: пользователь отменяет («отмени») — черновик закрывается, ничего не создаётся.

Альтернативный поток 4: задача со сроком без времени — создаётся с датой, без точного времени.

Обработка ошибок: занятое время встречи — 409 с указанием конфликта (Use Case 7); недоступен AI или база — ошибка сервиса, операция не маскируется успехом.

Постусловие: запись сохранена и участвует в списках, поиске и уведомлениях; либо ничего не создано.

Требования: FR-010–FR-013, FR-030, FR-031, FR-040.

## Use Case 2. Просмотр списка и ближайшего времени (Core MVP)

Актор: пользователь.

Цель: узнать планы, не глядя в интерфейс.

Основной поток:

1. «Что у меня завтра?» — ассистент определяет период и фильтры, неназванный период не придумывает.
2. Backend выбирает записи пользователя в его часовом поясе.
3. Ответ содержит список записей; пустой день — явный пустой список.

Альтернативный поток: «что мне сделать в течение часа?» — тот же интент с окном 60 минут; запись только с датой в окно не попадает.

Постусловие: данные только читаются.

Требования: FR-015, FR-016, FR-033.

## Use Case 3. Семантический поиск (Core MVP)

Актор: пользователь.

Цель: найти старую запись без точной формулировки.

Основной поток:

1. «Найди задачу про договор» — тема попадает в поисковый запрос, тип и период — в фильтры.
2. Backend объединяет буквальное совпадение названия и векторный поиск.
3. Ответ содержит найденные записи; пустой результат — валидный ответ.

Альтернативный поток: тема не названа — уточнение без выдуманного запроса.

Обработка ошибок: векторный поиск недоступен — работает буквальный.

Постусловие: данные только читаются.

Требования: FR-034.

## Use Case 4. Удаление записей (бонус ТЗ)

Актор: пользователь.

Цель: удалить одну или несколько записей без риска ошибиться.

Основной поток:

1. «Удали встречу с Иваном» — ассистент только ищет кандидатов.
2. Backend показывает пронумерованный список (даже из одной записи) и сохраняет его.
3. Пользователь выбирает номера: «№2», «удали первый и третий», «все показанные».
4. Backend проверяет выбор и удаляет записи одной операцией. Ответ подтверждает удаление с перечнем.

Альтернативный поток: «удали» без признаков — уточнение; случайный выбор исключён.

Обработка ошибок: запись изменилась или исчезла после показа — 409, ничего не удалено.

Постусловие: выбранное удалено целиком либо ничего не удалено.

Требования: FR-035, FR-036, FR-037.

## Use Case 5. Изменение записи и отметка выполнения (бонус ТЗ)

Актор: пользователь.

Цель: исправить или закрыть запись голосом или текстом.

Основной поток:

1. «Перенеси встречу с Иваном на завтра в 16:00» — ассистент находит записи и предлагаемые изменения.
2. Backend показывает кандидатов с номерами и предлагаемые значения; база пока не меняется.
3. Пользователь выбирает номер; backend сверяет снимок и обновляет запись (смена названия обновляет и вектор поиска). Ответ содержит обновлённую запись.

Альтернативный поток: «отметь задачу с отчётом выполненной» — тот же сценарий, меняется статус.

Обработка ошибок: «да» без номеров выбором не считается; устаревший выбор — 409.

Постусловие: выбранные записи изменены либо база не тронута.

Требования: FR-032, FR-035, FR-036.

## Use Case 6. Голосовой запрос

Актор: пользователь.

Цель: выполнить любой сценарий голосом.

Основной поток:

1. Клиент отправляет WAV-файл (до 20 MiB) в POST /api/task.
2. Backend распознаёт речь локально и обрабатывает текст как обычный запрос.
3. Ответ возвращается текстом.

Обработка ошибок: превышен размер — 413; сбой распознавания — 502/504.

Ограничение: голосового ответа (TTS) нет.

Требования: FR-020, FR-021.

## Use Case 7. Встреча на занятое время

Актор: пользователь.

Цель: избежать накладок.

Основной поток:

1. «Назначь встречу с Иваном завтра в 15:00».
2. Backend находит пересечение с активной встречей пользователя и занятостью Google.
3. Встреча не создаётся: 409 с указанием конфликтующей встречи.

Альтернативный поток: пользователь называет другое время с тем же task_id — встреча создаётся.

Обработка ошибок: ошибка проверки Google не блокирует создание по локальной базе.

Постусловие: встреча создана на свободное время либо не создана.

Требования: FR-040, FR-041.

## Use Case 8. Подключение Google Calendar

Актор: пользователь.

Цель: новые встречи появляются в календаре.

Основной поток:

1. Запрос на подключение возвращает адрес страницы согласия Google.
2. Пользователь подтверждает доступ; Google возвращает браузер на callback.
3. Backend обменивает код на токены и сохраняет подключение.

Альтернативный поток: отказ пользователя или истёкший state — возврат с признаком ошибки.

Обработка ошибок: интеграция не настроена — 503 google_disabled.

Постусловие: новые встречи синхронизируются. Refresh token в режиме Testing живёт 7 дней — затем подключение повторяется.

Требования: FR-060, FR-061.

## Use Case 9. Получение напоминания

Актор: пользователь.

Цель: узнать о событии вовремя.

Основной поток:

1. Планировщик заранее рассчитывает моменты уведомлений и сохраняет их.
2. В момент срабатывания уведомление доставляется по WebSocket; клиент подтверждает получение.
3. При настроенном SMTP дублируется письмом.

Альтернативный поток: клиент офлайн — уведомление досылается при следующем подключении; через 30 дней не подтверждённое удаляется.

Постусловие: пользователь получил уведомление или оно ожидает доставки.

Требования: FR-050–FR-054.

# Architecture Decision Records

Статус Accepted означает, что решение реализовано и действует. Если обоснование решения не сохранилось в материалах, это указано.

## ADR-001. Разделение backend (Go) и AI-service (Python FastAPI)

Статус: Accepted.

Контекст. Проекту нужны и быстрый API с работой с данными, и ML-стек: клиент LLM, torch, E5-эмбеддинги.

Рассмотренные альтернативы: один сервис на Go с прямыми вызовами LLM и ONNX-эмбеддингами.

Решение: два сервиса. Backend на Go отвечает за API, правила и хранение; ai-service на FastAPI — за LLM, контекст диалога и эмбеддинги. Взаимодействие по HTTP-контракту contracts/ai.openapi.yaml.

Последствия. Независимое масштабирование и деплой ML-части, тяжёлые Python-зависимости не попадают в backend. Цена — сетевой хоп и необходимость синхронизировать контракт (тест равенства копии в ai-service, генерация клиента в backend).

## ADR-002. LLM — Cloud.ru Foundation Models (GigaChat)

Статус: Accepted. Обоснование выбора провайдера взято из материалов PM, а не из кода.

Контекст. По ФЗ-149 и ФЗ-152 персональные данные не должны передаваться иностранным сервисам.

Рассмотренные альтернативы: прямое использование OpenAI и подобных (отклонено — трансграничная передача данных); локальная self-hosted LLM (не выбрана).

Решение: единственный провайдер — Cloud.ru Foundation Models, модель GigaChat. OpenAI-совместимый API, temperature 0.5, одна исправляющая попытка после невалидного ответа модели.

Последствия. Зависимость от внешнего API и квот. Ошибки провайдера нормированы кодами model_*. Недоступность провайдера возвращает 502/504, операция не выполняется.

## ADR-003. Локальный ASR — sherpa-onnx, GigaAM v3 CTC int8

Статус: Accepted. Переход с Zipformer на GigaAM — коммит 83cb182.

Контекст. Голос не должен покидать контур продукта; критичны точность на коротких командных репликах и потребление памяти.

Рассмотренные альтернативы: облачный STT (отклонён — передача аудио наружу); Zipformer RU (остался поддерживаемой конфигурацией: CER 0.0183–0.0121 против 0.0073 у GigaAM).

Решение: офлайн-распознаватель sherpa-onnx с GigaAM v3 NeMo CTC int8: 16 kHz, greedy, CPU, 2 потока. Модель скачивается при установке (make download-model).

Последствия. Аудио не покидает backend. По бенчмарку: задержка 241 мс, RAM 330 МБ. Модель весит сотни МБ и должна быть скачана до старта; выбор конфигурации идёт по наличию файлов модели.

## ADR-004. PostgreSQL + pgvector вместо отдельной векторной БД

Статус: Accepted.

Контекст. Записи хранятся в PostgreSQL; поиск нужен и по названию, и по смыслу.

Рассмотренные альтернативы: отдельный векторный движок (Qdrant, Milvus и подобные).

Решение: расширение pgvector и таблица task_embeddings: векторы названий E5 (384 измерения), cosine-поиск, порог 0.6, до 20 векторных кандидатов. Результат объединяется с буквальным совпадением названия; при недоступности векторной ветки буквальный работает.

Последствия. Транзакционность и один источник данных, общие фильтры доступа. Порог 0.6 не откалиброван (OQ-15). Смена версии модели требует пересчёта всех векторов.

## ADR-005. Redis для краткоживущего состояния

Статус: Accepted.

Контекст. Контексту диалога, сессиям и OAuth state нужен автоматический срок жизни.

Рассмотренные альтернативы: хранение в PostgreSQL с ручной очисткой.

Решение: Redis хранит контекст диалога и черновики (24 часа, продлевается), сессии авторизации, OAuth state (10 минут) и снимки кандидатов.

Последствия. Простое автоматическое устаревание. Потеря Redis означает перелогин и потерю активных диалогов; записи в PostgreSQL не затрагиваются.

## ADR-006. Nginx как единая точка входа

Статус: Accepted.

Контекст. Нужен публичный адрес для frontend и API; ai-service не должен быть доступен снаружи.

Рассмотренные альтернативы: прямой проброс портов сервисов.

Решение: Nginx раздаёт frontend и проксирует /api/ в backend на публичном порту 8088; на закрытом порту 8091 направляет запросы backend к ai-service. Отдельные таймауты под WebSocket (3600 с) и длинные LLM-запросы (240 с); лимит тела 20 MiB синхронизирован с backend.

Последствия. Один публичный адрес, ai-service закрыт; горизонтальное масштабирование через upstream с Docker DNS.

## ADR-007. Двухфазные изменение и удаление

Статус: Accepted.

Контекст. Удаление — деструктивная операция; модель и пользователь могут ошибиться. CustDev требует защиты от неверных действий.

Рассмотренные альтернативы: выполнять удаление по одной реплике (отклонено — риск массовой ошибки).

Решение. Интенты on_delete и on_update работают в две фазы: поиск возвращает пронумерованных кандидатов (для изменения — и предлагаемые значения) и сохраняет снимки в Redis; действие выполняется только по явному выбору номеров, сверенному со снимками и владельцем. Устаревший выбор даёт 409 без частичного применения. Выбор номеров распознаётся локально в ai-service, без вызова LLM.

Последствия. Защита данных ценой двух запросов и логики инвалидации снимков.

## ADR-008. Контракт-first с генерацией кода

Статус: Accepted.

Контекст. Три потребителя API и два контракта; ручное дублирование типов даёт расхождения.

Рассмотренные альтернативы: описывать типы вручную или генерировать из кода.

Решение. Источники — contracts/backend.openapi.yaml и contracts/ai.openapi.yaml. Backend генерирует серверный код и клиент AI через oapi-codegen; ai-service хранит копию контракта и проверяет её равенство тестом. Архивные спецификации помечены как неактуальные.

Последствия. Типы всегда соответствуют контрактам. Любое изменение API начинается с YAML. Копия в ai-service/app/resources обязательна для старта приложения.

## ADR-009. Собственный WebSocket-хаб уведомлений

Статус: Accepted.

Контекст. Напоминания нужно доставлять в реальном времени, включая браузер, где WebSocket API не позволяет задать заголовок Authorization.

Рассмотренные альтернативы: внешний push-сервис (лишняя зависимость для текущего этапа); опрос клиентом.

Решение. WebSocket-хаб в backend: авторизация первым сообщением в течение 5 секунд, ready → notification → ack, досылка неподтверждённых после переподключения, хранение 30 дней. Email — параллельный канал.

Последствия. Доставка офлайн-клиенту при следующем подключении. Мобильный push остаётся нереализованным (OQ-02).

## ADR-010. Планировщик напоминаний на предвычисленных моментах

Статус: Accepted.

Контекст. Уведомления должны приходить в конкретные моменты с учётом часового пояса и переживать перезапуск.

Рассмотренные альтернативы: опрос записей на лету; внешние планировщики.

Решение. Планировщик синхронизирует окно 7 дней каждые 10 минут и создаёт строки notifications: точный момент события и опережения 72 часа, 24 часа, 3 часа, 10 минут (опережение — только если до него больше 5 часов). Записи без времени уведомляются в 09:00 часового пояса. Параметры настраиваются переменными REMINDER_*.

Последствия. Перезапуск не теряет уведомления (персистентны в БД). Claim TTL 2 минуты защищает от параллельной обработки одной строки.

# Архитектура

Принятые решения и их обоснования - в [ADR](adr.md). Диаграммы - Structurizr DSL в [diagrams](../diagrams/): architecture.dsl - четыре вида: SystemContext, Containers, компоненты backend и ai-service; task-flow.dsl - поток запроса; notifications.dsl - уведомления; database.dsl - схема данных.

## 1. Компоненты

- Nginx - единая точка входа: раздаёт собранный frontend, направляет API-запросы в backend (публичный порт 8088) и внутренние вызовы backend → ai-service (закрытый порт 8091). Отдельные таймауты под WebSocket и длинные запросы к LLM.
- Backend (Go 1.26, chi) - HTTP API, авторизация, распознавание речи (sherpa-onnx), бизнес-правила, операции с PostgreSQL, планировщик напоминаний, WebSocket-хаб, отправка email. Порт 8080.
- AI-service (Python 3.12, FastAPI) - разбор запроса через LLM, формулировка ответа, вычисление E5-эмбеддингов. Порт 8090.
- PostgreSQL 16 с расширением pgvector - записи, пользователи, векторы, подключения Google, уведомления.
- Redis 7 - краткоживущее состояние: контекст диалога (24 часа), сессии авторизации (24 часа), OAuth state (10 минут), снимки кандидатов.
- Mailpit - dev-сервер почты; в рабочем окружении заменяется реальным SMTP.
- Внешние сервисы: Cloud.ru Foundation Models (GigaChat), Google Calendar API, SMTP-сервер.

## 2. Принципы

Модель предлагает - backend исполняет. LLM возвращает действие по схеме и не знает результатов операций. Backend проверяет действие, владельца и правила, выполняет операцию и передаёт фактический результат в /api/respond для формулировки ответа. Сбой генерации заменяет сообщение резервным текстом, операция сохраняется.

Деструктивные операции - в два шага. Изменение и удаление сначала показывают пронумерованных кандидатов. Действие выполняется только по явному выбору, сверенному с сохранёнными снимками записей.

Данные с разными сроками жизни. PostgreSQL - источник правды. Redis хранит только то, что устаревает само: контекст, сессии, состояние OAuth. Потеря Redis означает перелогин и начало диалогов заново, записи не страдают.

## 3. Путь запроса

1. Клиент отправляет текст или WAV в backend через Nginx (POST /api/task).
2. WAV распознаётся локальной моделью через sherpa-onnx и превращается в текст.
3. Backend передаёт текст, время и контекст в ai-service (/api/job) и получает действие или уточняющий вопрос.
4. Backend валидирует действие и выполняет операцию в PostgreSQL: проверяет владельца, конфликты, снимки выбора.
5. Backend передаёт результат в ai-service (/api/respond) и получает формулировку ответа; при сбое - резервный текст.
6. Клиент получает статус (ok, needs_clarification, candidates и другие), task_id, данные и заголовок X-Task-Intent.

Планировщик напоминаний работает независимо от запросов: сканирует записи каждые 30 секунд, рассчитывает моменты уведомлений и передаёт их в WebSocket-хаб и email-воркер.

# GorkyCode AI-service

FastAPI-сервис с четырьмя операциями:

| Операция | Назначение |
|---|---|
| `GET /health` | Проверка жизни процесса; не проверяет доступность Cloud.ru или E5 |
| `POST /api/job` | Интерпретация календарного запроса через Cloud.ru |
| `POST /api/embed` | Векторизация одного текста настоящей локальной CPU-моделью E5 |
| `POST /api/respond` | Формулировка ответа по фактическому результату backend |

Канонический контракт: [contracts/ai.openapi.yaml](../contracts/ai.openapi.yaml).
Сервис возвращает структурированные действия и векторы. Хранение записей,
SQL, векторный индекс и выдача результатов поиска относятся к интеграции backend.

`on_delete` работает в два шага: AI подготавливает поиск кандидатов, а после
выбора пользователем сопоставляет показанные номера с ID записей. Поиск и
фактическое удаление выполняет backend.

## Подготовка

Все команды ниже выполняются из каталога сервиса:

```bash
cd ai-service
```

Если `.env` ещё нет, создайте его из шаблона:

```bash
cp .env.example .env
```

Задайте `CLOUDRU_API_KEY` и `CLOUDRU_MODEL`. Получение ключа и параметры:
[настройка Cloud.ru](docs/cloudru-setup.md). Существующий `.env` заменять не нужно.

## Запуск

На хосте нужен Python 3.12 с venv:

```bash
bash scripts/run_host_service.sh
```

Для Docker нужны Docker Engine и Python 3.10+ на хосте:

```bash
bash scripts/run_docker_service.sh
```

Выберите один режим и дождитесь `READY`. По умолчанию адрес на хосте —
`http://127.0.0.1:8090`, в Docker — `http://127.0.0.1:8091`.
Документация отключена по умолчанию. Для локального просмотра задайте
`SECURITY_EXPOSE_DOCS=true`: Swagger `/docs`, ReDoc `/redoc`. Ctrl+C в терминале launcher
останавливает созданный им сервис. Подробности: [запуск и быстрая проверка](docs/cloudru-live-testing.md).

## Проверки

Статические проверки в хостовом окружении с установленными dev-зависимостями:

```bash
.venv/bin/python -m pytest -q -p no:cacheprovider tests/unit tests/test_embeddings_encoder.py
```

Для установки dev-зависимостей используйте раздел «Статические тесты»
в [гайде тестирования](docs/service-live-testing.md).

После запуска сервиса во втором терминале выберите тот же runtime.
Один реальный Cloud.ru-сценарий:

```bash
python3 scripts/test_cloudru_live.py --runtime host
# Для Docker: --runtime docker
```

Контракт, валидация и настоящая E5 без обращений к Cloud.ru:

```bash
python3 scripts/test_service_live.py --runtime host --sections contract,validation,embeddings
```

Полный live-набор с Cloud.ru и отдельными fault-процессами:

```bash
python3 scripts/test_service_live.py --runtime host
```

Генерации расходуют квоту Cloud.ru. Полный runner содержит 153 тестовых метода.
Список без сетевых запросов:

```bash
python3 scripts/test_service_live.py --list
```

Обычный pytest пропускает live-тесты: для них нужен отдельный runner с работающим
сервисом. Число собранных тестов не означает их успешное прохождение.

## Правила API

Сервис публикует по `/openapi.json` пакетный ресурс в формате OpenAPI 3.0.3.
При `SECURITY_EXPOSE_DOCS=true` Swagger/ReDoc показывают копию корневого контракта.

| Файл | Роль и текущее состояние |
|---|---|
| [Корневой контракт](../contracts/ai.openapi.yaml) | Источник истины для backend и AI-service |
| [app/resources/ai.openapi.yaml](app/resources/ai.openapi.yaml) | Читается при старте для примеров `/api/job` и публикации OpenAPI; включается в пакет и Docker |
| [contracts/ai.openapi.yaml](contracts/ai.openapi.yaml) | Дополнительное зеркало для контрактных тестов; приложение его не читает |

Обе локальные копии совпадают с корневым файлом.
Удаление `app/resources` сломает текущую загрузку приложения. Вложенный
`contracts/` можно убрать после изменения двух контрактных тестов и ссылок;
сейчас он остаётся в проекте.

### Реализованные действия

- `ready`: непустой `message`, полное `action`, `context.draft=null`.
  Действия: `create_event`, `list_events`, `search_events`, `on_delete`, `on_update`.
- `needs_clarification`: вопрос пользователю, `action=null`, текущий черновик
  в context. Следующий запрос передаёт фактический context предыдущего ответа.
- Неподдерживаемое намерение возвращает HTTP 400 Problem с `unsupported_intent`.
- Историю и публичный ответ собирает код сервиса: при продолжении история
  сохраняется, при распознанной смене темы очищается. Новое action/draft содержит
  полное состояние темы; скрытого слияния со старым draft нет.
- `user_id` и `task_id` переносятся из запроса. Модель в `/api/job` не видит
  результаты БД и не должна придумывать количество или состав найденных записей.
  После выполнения действия backend вызывает `/api/respond` с фактическим
  результатом; этот вызов формирует сообщение пользователю. Если генерация
  недоступна, backend возвращает резервное сообщение, сохраняя результат операции.
- `/api/embed` возвращает только `embedding`, `model`, `model_version`.
  Ошибки API имеют формат `application/problem+json`; code не ограничен enum.
  Ошибки валидации запроса возвращаются как 400.

### Удаление `on_delete`

В корневом контракте описаны `X-Task-Intent: on_delete`, контекст со списком
кандидатов, фазы `find_candidates` и `delete_confirmed`, сопоставление выбранных
номеров с `action.task_ids`. В JSON новых delete-ответов поля `intent` нет;
старые create/list/search продолжают использовать JSON intent.

При `find_candidates` AI возвращает все поля фильтра, незаданные — `null`.
Backend показывает пользователю найденные записи с номерами и кладёт кандидатов
в контекст следующего запроса. При `delete_confirmed` модель выбирает номера;
код AI-сервиса сопоставляет их с ID из контекста и отвергает неизвестные номера.
AI не обращается к БД и не удаляет записи. Backend повторно проверяет ID и
владельца, затем удаляет все выбранные строки одной транзакцией. Если ответ
пользователя после показа кандидатов неясен, AI повторяет поиск, чтобы список
не пропал из контекста следующего запроса.

### Изменение `on_update`

AI возвращает `X-Task-Intent: on_update` без поля `intent` в JSON. В фазе
`find_candidates` он передаёт фильтры прежних записей и объект `changes`
с новыми значениями. Backend показывает пронумерованных кандидатов и хранит
предлагаемые изменения до выбора. В фазе `update_confirmed` модель выбирает
только показанные номера; код AI сопоставляет их с UUID записей. Backend
проверяет владельца и актуальность выбора, затем изменяет выбранные записи
одной транзакцией. Простое «да» не считается выбором.

## Семантическая часть

`/api/job` через Cloud.ru извлекает тему и фильтры. `/api/embed` независимо
вычисляет вектор; автоматической связки между endpoint внутри сервиса нет.
Клиент передаёт текст без префиксов. Наш encoder выполняет NFC и strip по краям,
добавляет `passage: ` для document или `query: ` для query, токенизирует с правым
усечением до 512 токенов. Регистр и внутренние пробелы сохраняются.

Настоящая CPU-модель `intfloat/multilingual-e5-small` возвращает 384 L2-нормированные
координаты и идентификаторы `model`/`model_version`. Хранение document-векторов,
совместимость версий, фильтрация, ранжирование и объединение с буквальным поиском
относятся к интеграции backend. Технические E5-тесты не устанавливают порог
релевантности. Корпус 60 документов/40 запросов сохранён в fixtures, но текущий
runner его не использует; действующего evaluator ранжирования нет.

## Защита действий и границы доверия

`SECURITY_GUARD_MODE=enforce` включён по умолчанию. Для модельных готовых
действий создания, поиска кандидатов для изменения и удаления требуется отдельная
проверяющая модель: укажите `SECURITY_GUARD_MODEL` с реальным ID из вашего аккаунта.
Используется отдельный Cloud.ru client с тем же API key/base URL, без повторных
попыток. Модель не выбирается автоматически. До настройки записи возвращают 503;
health, чтение и шаблонный `/api/respond` продолжают работать. Создание с подтверждением
пользователя не добавлено: это требует отдельного согласованного сценария.

Проверяется окончательное публичное действие после нормализации дат и повышения
черновика до готового действия. `allow` допускает действие; `block` и `clarify`
возвращают существующий 400 `unsupported_intent` без отклонённого action/draft.
Недоступность, некорректный verdict и timeout дают 503. Поиск/список не вызывают
проверяющую модель. Явный выбор номеров из сохранённых кандидатов исполняется
существующей программной проверкой и сопоставлением ID, без обеих моделей.
`X-Task-Intent` и публичные схемы не изменены.

`SECURITY_GUARD_MODE=observe` предназначен только для явной диагностической настройки:
он **не блокирует** действия при отказе/ошибке/отсутствии проверяющего. Он не обеспечивает
защиту записи. Дополнительная модель снижает риск ошибки, но не доказывает соответствие
намерению; ограничения владельца и реальное исполнение остаются ответственностью backend.

Настройки: guard timeout 15 секунд, max tokens 256, max concurrency 4. Ожидание
свободного слота входит в timeout; отмена освобождает слот. Общий
`JOB_TIMEOUT_SECONDS` включает основную модель, исправление JSON и проверку.
Внедрённые clients принадлежат вызывающему коду; lifespan закрывает только свои.
В логах проверки присутствуют только фиксированные reason/error коды и длительность.

Запросы ограничены до разбора JSON: `/api/job` 262144 байта,
`/api/respond` 524288 байт, включая потоки без Content-Length. Чтение body ограничено
`JOB_TIMEOUT_SECONDS`. Превышение даёт 413; таймаут загрузки — 408.
`/api/embed` сохраняет собственные ограничения. Дополнительные настройки:

- `SECURITY_USER_MAX_CHARS=8192` — текущий текст.
- `SECURITY_HISTORY_MESSAGE_MAX_CHARS=8192` — сообщение сохранённой истории.
- `SECURITY_CONTEXT_MAX_CHARS=32768` — сериализованный эффективный контекст.

Для истории сначала выбираются последние 20 сообщений, затем проверяются бюджеты.
Кандидаты в модельном контексте содержат только исходные номера. Команды, черновики
и изменения не обрезаются: при превышении запрос отклоняется целиком.
Проверяется также итоговый контекст после добавления текущего хода: переполнение
не возвращается клиенту как пригодное для продолжения состояние. Значения
выбраны с запасом относительно коротких календарных сценариев fixtures; их можно
явно изменить для своего трафика в пределах валидируемых настроек.

`/api/respond` и готовые сообщения `/api/job` используют шаблоны. Названия, текст
запроса и произвольные значения изменений в них не интерполируются, чтобы не
попадать обратно в историю ассистента. Вторая модель получает минимальный контекст,
а не названия/ID кандидатов или свободные ответы ассистента. Подозрительные строки
не удаляются словарным фильтром: такие фильтры не являются границей безопасности.


## Дополнительная защита от раскрытия

В ветку `promt_injection` перенесены защитные механизмы адаптации к main с
сохранением текущего API-контракта. Свободный `message` внутреннего извлекателя
не публикуется и не добавляется в историю: уточнения и готовые сообщения
формируются шаблонами. Все пути выдачи, включая программный выбор кандидатов,
проверяют лимиты и утечки; модельные готовые действия записи дополнительно
проходят ActionGuard.

`DisclosurePolicy` отклоняет вход с настроенным ключом Cloud.ru и его обычными
Base64/hex-представлениями до вызова модели. Перед выдачей проверяются сообщение,
действие и черновик на этот ключ, длинные точные фрагменты обоих внутренних
промптов и некоторые простые преобразования. Ошибки не содержат найденные
значения. Пересказ, произвольное шифрование и все варианты обфускации эта проверка
не покрывает; секретам не место в системных промптах.

Документация отключена по умолчанию (`SECURITY_EXPOSE_DOCS=false`); ответы
получают `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`.
Стандартные launcher отключают заголовок сервера. Это дополнительные меры,
которые не заменяют аутентификацию. AI endpoints должны вызываться доверенным
backend: переданный в JSON `user_id` сам по себе не удостоверяет личность.

После слияния `main` сохранены `chat` и отмена черновика, статус `in_progress`,
необязательный период списка, фильтры `statuses`/`upcoming_minutes`, относительные
напоминания и восстановление смены статуса. Эти возможности соответствуют
обновлённому общему API-контракту main.

Для обычного `chat` выполняется отдельный короткий stateless-вызов с публичной
инструкцией, текущей репликой и последними шестью пользовательскими сообщениями.
Внутренний промпт извлекателя, история ассистента, черновик и кандидаты туда не
передаются. Явные просьбы раскрыть внутренние инструкции, ключи или чужие данные
получают фиксированный отказ. Сгенерированные URL удаляются из разговорного
ответа; названия записей не переписываются. Календарные уточнения используют
`safe_messages` без дополнительного вызова модели. `/respond` остаётся шаблонным.

Резервное восстановление смены статуса проходит ту же `_response` с проверкой
утечек и ActionGuard. Guard по-прежнему требует настроенной
`SECURITY_GUARD_MODEL`; `observe` не блокирует действия по вердикту guard.

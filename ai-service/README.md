# GorkyCode AI-service

FastAPI-сервис с тремя операциями:

| Операция | Назначение |
|---|---|
| `GET /health` | Проверка жизни процесса; не проверяет доступность Cloud.ru или E5 |
| `POST /api/job` | Интерпретация календарного запроса через Cloud.ru |
| `POST /api/embed` | Векторизация одного текста настоящей локальной CPU-моделью E5 |

Канонический контракт: [contracts/ai.openapi.yaml](../contracts/ai.openapi.yaml).
Сервис возвращает структурированные действия и векторы. Хранение записей,
SQL, векторный индекс и выдача результатов поиска относятся к интеграции backend.

**Текущее ограничение:** корневой контракт уже включает удаление `on_delete`,
но эта операция ещё не реализована. Обе копии YAML внутри `ai-service` содержат
предыдущую версию. Приложение публикует старую схему; полное соответствие
актуальному корневому контракту сейчас не достигнуто.

## Подготовка

Все команды ниже выполняются из каталога сервиса:

```bash
cd /home/kandratt/Desktop/GorkyCode/ai-service
```

Если `.env` ещё нет, создайте его из шаблона:

```bash
cp .env.example .env
```

Задайте `CLOUDRU_API_KEY` и `CLOUDRU_MODEL`. Получение ключа и параметры:
[настройка Cloud.ru](docs/cloudru-setup.md). Существующий `.env` заменять не нужно.

## Запуск

На хосте нужен Python 3.12 с venv:

```bash
bash scripts/run_host_service.sh
```

Для Docker нужны Docker Engine и Python 3.10+ на хосте:

```bash
bash scripts/run_docker_service.sh
```

Выберите один режим и дождитесь `READY`. По умолчанию адрес на хосте —
`http://127.0.0.1:8090`, в Docker — `http://127.0.0.1:8091`.
Swagger доступен по `/docs`, ReDoc — по `/redoc`. Ctrl+C в терминале launcher
останавливает созданный им сервис. Подробности: [запуск и быстрая проверка](docs/cloudru-live-testing.md).

## Проверки

Статические проверки в хостовом окружении с установленными dev-зависимостями:

```bash
.venv/bin/python -m pytest -q -p no:cacheprovider tests/unit tests/test_embeddings_encoder.py
```

Для установки dev-зависимостей используйте раздел «Статические тесты»
в [гайде тестирования](docs/service-live-testing.md).

После запуска сервиса во втором терминале выберите тот же runtime.
Один реальный Cloud.ru-сценарий:

```bash
python3 scripts/test_cloudru_live.py --runtime host
# Для Docker: --runtime docker
```

Контракт, валидация и настоящая E5 без обращений к Cloud.ru:

```bash
python3 scripts/test_service_live.py --runtime host --sections contract,validation,embeddings
```

Полный live-набор с Cloud.ru и отдельными fault-процессами:

```bash
python3 scripts/test_service_live.py --runtime host
```

Генерации расходуют квоту Cloud.ru. Полный runner содержит 153 тестовых метода.
Список без сетевых запросов:

```bash
python3 scripts/test_service_live.py --list
```

Обычный pytest собирает 67 статических проверок и пропускает 153 live-теста:
для них нужен отдельный runner с работающим сервисом. Число собранных тестов
не означает их успешное прохождение. Пока контракты расходятся, статическая
и live-проверка синхронизации контракта не могут пройти.

## Правила API

Сервис публикует по `/openapi.json` пакетный ресурс в формате OpenAPI 3.0.3.
Swagger/ReDoc показывают эту локальную схему, которая сейчас отстаёт от канона.

| Файл | Роль и текущее состояние |
|---|---|
| [Корневой контракт](../contracts/ai.openapi.yaml) | Источник истины; уже включает `on_delete` |
| [app/resources/ai.openapi.yaml](app/resources/ai.openapi.yaml) | Читается при старте для примеров `/api/job`, публикации OpenAPI и тестового экспорта; включается в Python-пакет и Docker. Старая версия |
| [contracts/ai.openapi.yaml](contracts/ai.openapi.yaml) | Дополнительное зеркало для текущих контрактных тестов; приложение его не читает. Старая версия |

Обе локальные копии совпадают друг с другом, но отличаются от корневого файла.
Удаление `app/resources` сломает текущую загрузку приложения. Вложенный
`contracts/` можно убрать после изменения двух контрактных тестов и ссылок;
сейчас он остаётся в проекте.

### Реализованные действия

- `ready`: непустой `message`, полное `action`, `context.draft=null`.
  Действия: `create_event`, `list_events`, `search_events`.
- `needs_clarification`: вопрос пользователю, `action=null`, текущий черновик
  в context. Следующий запрос передаёт фактический context предыдущего ответа.
- Неподдерживаемое намерение возвращает HTTP 400 Problem с `unsupported_intent`.
- Историю и публичный ответ собирает код сервиса: при продолжении история
  сохраняется, при распознанной смене темы очищается. Новое action/draft содержит
  полное состояние темы; скрытого слияния со старым draft нет.
- `user_id` и `task_id` переносятся из запроса. Готовый `message` показывается
  потребителем после успешного выполнения действия. Модель не видит результаты БД
  и не должна придумывать количество или состав найденных записей.
- `/api/embed` возвращает только `embedding`, `model`, `model_version`.
  Ошибки API имеют формат `application/problem+json`; code не ограничен enum.
  Ошибки валидации запроса возвращаются как 400.

### Что требуется для нового on_delete

В корневом контракте описаны `X-Task-Intent: on_delete`, контекст со списком
кандидатов, фазы `find_candidates` и `delete_confirmed`, сопоставление выбранных
номеров с `action.task_ids`. В JSON новых delete-ответов поля `intent` нет;
старые create/list/search продолжают использовать JSON intent.

Эти схемы, заголовок и обработка диалога удаления ещё отсутствуют в коде сервиса.
Текущий live-тест `unsupported_delete` ожидает отказ в удалении, поэтому набор
также предстоит адаптировать к новому контракту. Проверка владельца/кандидатов
и транзакционное удаление строк относятся к обязанностям backend по контракту;
состояние его реализации здесь не проверялось.

Для согласования нужны изменения моделей запросов/ответов, prompt, сервисной
логики и HTTP-заголовка, новые тесты, синхронизация поставляемой схемы и
пересборка/перезапуск. Одно копирование нового YAML не реализует `on_delete`.

## Семантическая часть

`/api/job` через Cloud.ru извлекает тему и фильтры. `/api/embed` независимо
вычисляет вектор; автоматической связки между endpoint внутри сервиса нет.
Клиент передаёт текст без префиксов. Наш encoder выполняет NFC и strip по краям,
добавляет `passage: ` для document или `query: ` для query, токенизирует с правым
усечением до 512 токенов. Регистр и внутренние пробелы сохраняются.

Настоящая CPU-модель `intfloat/multilingual-e5-small` возвращает 384 L2-нормированные
координаты и идентификаторы `model`/`model_version`. Хранение document-векторов,
совместимость версий, фильтрация, ранжирование и объединение с буквальным поиском
относятся к интеграции backend. Технические E5-тесты не устанавливают порог
релевантности. Корпус 60 документов/40 запросов сохранён в fixtures, но текущий
runner его не использует; действующего evaluator ранжирования нет.

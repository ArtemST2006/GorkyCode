# Ревью обработки запросов — 26 октября 2026

## Исправлено

- Параллельные запросы одного пользователя с одним `task_id` защищены блокировкой Redis. Второй запрос получает HTTP 409, пока первый обрабатывается. Блокировка действует между экземплярами backend, освобождается при ошибке и имеет срок жизни на случай остановки процесса.
- Контекст и снимок кандидатов публикуются в Redis одной транзакцией с одинаковым сроком хранения. Подтверждение проверяется по кандидатам именно текущей реплики и по текущей операции.
- Удаление сверяет содержимое записей с показанными кандидатами. Если запись изменилась или исчезла, весь запрос отклоняется с 409. Обновление и удаление блокируют строки в одинаковом порядке, чтобы пересекающиеся выборки не создавали взаимную блокировку.
- Вопросы с номерами, отрицания, время и команда другой операции не считаются подтверждением. Например, «Что в записи №1?» не удаляет её, а «Удали №1» не подтверждает ранее предложенное изменение.
- Повторный поиск кандидатов на изменение сохраняет только заданные поля `changes`, без запрещённых `null`, которые могли приводить к ошибке AI-сервиса.
- Multipart-запрос отклоняется, если одновременно переданы текст и аудио, несколько файлов или дублирующиеся поля. `user_id` читается из тела, а не из query string.
- Фильтр участника встречи работает независимо от регистра. «С понедельника» не добавляется к поисковому запросу как имя участника.
- История, отправляемая модели и возвращаемая в контексте, ограничена последними 20 сообщениями. Текущий `draft` и кандидаты сохраняются отдельно.
- OpenAPI и сгенерированные Go-модели синхронизированы.

## Проверки

- Все пакеты backend: `go test -race ./...`, с подключёнными PostgreSQL и Redis.
- Конкурентные UPDATE/UPDATE и UPDATE/DELETE из разных диалогов, обратный порядок выбранных ID, устаревшее содержимое, атомарность удаления и изоляция владельца.
- Блокировка Redis между клиентами; позднее освобождение старой блокировки не снимает новую. Второй параллельный запрос не вызывает AI повторно.
- 89 локальных тестов Python: контракты, подтверждения, даты, история и encoder. Платная языковая модель в этих тестах не вызывается.
- Реальный локальный embedding encoder + PostgreSQL: Иван/Таня в разных регистрах, отсутствие нужного человека, стоматолог/зубной врач, билеты/проездные документы, изоляция чужих записей.
- 47 примеров запросов и ответов из двух OpenAPI проверены по схемам.

## Оставшиеся ограничения

- `multilingual-e5-small` может давать лишние совпадения для коротких неоднозначных запросов. На контрольных данных «про слайды» сблизило и презентацию, и покупку билетов. Снижение общего порога также теряет полезные совпадения; для повышения точности нужен отдельно проверенный reranker или более качественная embedding-модель.
- Запись без embedding (например, если encoder был недоступен при создании) доступна по буквальному поиску, но может не находиться по синонимам. В этом ревью массовое переиндексирование не выполнялось.
- Блокировка предотвращает одновременную обработку диалога, но не делает создание идемпотентным. Потерянный HTTP-ответ после успешного COMMIT и последующий новый запрос могут создать дубликат — текущий контракт этого не запрещает.
- После слияния `feat/calendar` создание пересекающейся встречи требует подтверждения. Продолжительность берётся из настройки `google.event_duration` (по умолчанию 1 час). Проверка пересечений не является транзакционным запретом: два одновременно создаваемых события всё ещё могут пройти проверку до записи друг друга.
- Полный набор формулировок через платную LLM в этом ревью не прогонялся. Проверены локальная логика и контракты; доступность провайдера и точность понимания всех формулировок не гарантируются.
